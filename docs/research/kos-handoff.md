# kOS handoff: delivering and running Claude-written scripts

Research for issue #2. Question: how can a KSP 1.12.5 mod hand a kerboscript to a vessel's kOS processor, start it, and learn when it finished and whether it succeeded?

Sources were read from the kOS `develop` branch at commit [`8f281a4`](https://github.com/KSP-KOS/KOS/tree/8f281a459b6ea0ba917c91bbbc117e68bb948199) (2026-05-14). That matches the latest release, [kOS 1.6.0.1](https://github.com/KSP-KOS/KOS/releases/tag/1.6.0.1). Below, `SRC` stands for `https://github.com/KSP-KOS/KOS/blob/8f281a459b6ea0ba917c91bbbc117e68bb948199/`.

## Answer

kOS has no formal, documented C# API for other mods to "run this script and tell me the result." What it does have is enough public surface to build that handoff reliably:

1. **Deliver.** Write the `.ks` file as plain text into the Archive folder, `<KSP>/Ships/Script/` (volume `0:/`). kOS reads it the next time a script opens that path, with no reload needed. The catch: a vessel can only reach `0:/` while it has a CommNet connection to home (or is in PRELAUNCH). If the vessel might be out of contact, the C# mod can write straight to the processor's local disk instead (`kOSProcessor.HardDisk`, a public property). The flight-time CommNet check does not apply to that path.
2. **Start.** There are three options, ordered from least to most coupled:
   - **(a) Simulated keystrokes.** `TermWindow.ProcessOneInputChar(...)` is public, and its source comment says it is "how other mods should send input to the terminal." The mod types `runpath("0:/claudia/seq_007.ks").` followed by Enter. This is the only entry point kOS explicitly endorses for other mods.
   - **(b) A resident boot script plus messages.** A small Claudia boot script on the processor waits on `CORE:MESSAGES`. The mod pushes a message into that queue from C# with the public `kOSProcessor.Send(Structure)` method, and the boot script then `runpath`s the file named in the message. This keeps the terminal free and does not depend on keystroke timing.
   - **(c) Direct CPU access through a kOS addon.** A `[kOSAddon("CLAUDIA")]` class gets each processor's `SharedObjects` (CPU, interpreter, volumes, screen) in its constructor. That lets the mod compile and push a program with `Cpu.RunProgram(...)`, or register an `IPopContextNotifyee` to hear when a program context ends. These are public members, but they are internals, not a supported API.
3. **Learn the result.** kOS signals a script's end in a generic way: the program context is popped. It does not signal success or failure. The recommended pattern is that Claudia wraps every Maneuver Sequence script so it reports its own outcome:
   - The script writes a result record with `WRITEJSON(lexicon, "0:/claudia/results/seq_007.json")` (needs a home connection), or calls a suffix on Claudia's own kOS addon, such as `ADDONS:CLAUDIA:REPORT(lex)`. The addon option works in-process with no connection needed and is the cleanest of the three.
   - A kOS runtime error aborts every running program and prints the error to the terminal (and partly to `KSP.log` with a `kOS:` prefix). Kerboscript has no try/catch (I believe; see the uncertainty notes). So an error appears as: "the program context ended, the interpreter is back at the prompt, and no success report arrived." The error text can then be read from the terminal screen buffer or from Unity's log stream.

**Recommendation for the decision ticket:** Use option (c)-lite. Ship a tiny kOS addon assembly, `ADDONS:CLAUDIA`, as the reporting channel and as the source of each processor's `SharedObjects`. Start scripts through (b) the boot-script message loop, or (a) keystroke injection as a fallback. Treat "context popped with no report" as failure, and grab the terminal text as the error detail.

## Detail

### 1. The Archive (`0:/`) and local volumes

- The Archive is a real directory: `GameDatabase.Instance.PluginDataFolder + "/Ships/Script/"`, which is `<KSP root>/Ships/Script/`. Source: [SRC src/kOS/Module/Bootstrapper.cs#L48-L54](https://github.com/KSP-KOS/KOS/blob/8f281a459b6ea0ba917c91bbbc117e68bb948199/src/kOS/Module/Bootstrapper.cs#L48-L54).
- The docs say files there are ordinary `.ks` text files that kOS sees "immediately by KOS the next time it tries running that program." They also note that the Archive is shared across all saves, is unlimited in size, does not revert with "revert flight", and that "editing the files in the Archive directory is allowed and in fact is an officially accepted way to use the plugin." Source: [ksp-kos.github.io/KOS/general/volumes.html](https://ksp-kos.github.io/KOS/general/volumes.html) ([rst](https://github.com/KSP-KOS/KOS/blob/8f281a459b6ea0ba917c91bbbc117e68bb948199/doc/source/general/volumes.rst)).
  - The same doc warns that the location "is likely to change to somewhere in GameData in a future version". That warning is old and has not come true as of 1.6.0.1. To avoid hard-coding the path, read `kOS.Safe.Utilities.SafeHouse.ArchiveFolder`, a public static. Source: [SRC src/kOS.Safe/Utilities/SafeHouse.cs](https://github.com/KSP-KOS/KOS/blob/8f281a459b6ea0ba917c91bbbc117e68bb948199/src/kOS.Safe/Utilities/SafeHouse.cs).
- **Archive reachability.** Each processor's volume manager range-checks the Archive. The check passes only if `vessel.situation == PRELAUNCH || ConnectivityManager.HasConnectionToHome(vessel)`; otherwise it throws `KOSVolumeOutOfRangeException`. Source: [SRC src/kOS/Persistence/ConnectivityVolumeManager.cs#L35-L44](https://github.com/KSP-KOS/KOS/blob/8f281a459b6ea0ba917c91bbbc117e68bb948199/src/kOS/Persistence/ConnectivityVolumeManager.cs#L35-L44). Which connectivity manager is used (CommNet, RemoteTech, or PermitAll) depends on the player's kOS settings. Source: [communication docs, "Connectivity Managers"](https://ksp-kos.github.io/KOS/commands/communication.html#connectivity-managers). Under CommNet, a probe behind the Mun cannot `runpath("0:/...")`. Delivery code must handle this, either by copying to `1:/` ahead of time or by writing to the HardDisk from C#.
- **Local disk.** Each processor has a `Harddisk` (volume 1, and so on). It is persisted inside the save file and its size is limited by `diskSpace`. `kOSProcessor.HardDisk` and `kOSProcessor.Archive` are public properties. Source: [SRC src/kOS/Module/kOSProcessor.cs#L35-L41](https://github.com/KSP-KOS/KOS/blob/8f281a459b6ea0ba917c91bbbc117e68bb948199/src/kOS/Module/kOSProcessor.cs#L35-L41). kOS itself uses `HardDisk.SaveFile(path, content)` to copy the boot file in. Source: [same file #L619-L635](https://github.com/KSP-KOS/KOS/blob/8f281a459b6ea0ba917c91bbbc117e68bb948199/src/kOS/Module/kOSProcessor.cs#L619-L635). So a mod can write files to a vessel's local disk directly, without a connection check. This is an inference from public members, not a documented use.

### 2. Boot files

- Any file in `0:/boot/` can be chosen as a processor's boot file. The choice is made in the editor PAW field `bootFile`, or through `CORE:BOOTFILENAME` (get/set) in script. The file is copied to the local disk when the vessel reaches PRELAUNCH (unless `CONFIG:ARCH` is true), and it runs "as soon as CPU boots, e.g. as soon as you bring your CPU in physics range or power on your CPU." Source: [volumes docs, "Special handling of files in the boot directory"](https://ksp-kos.github.io/KOS/general/volumes.html#special-handling-of-files-in-the-boot-directory); [kOSProcessor docs, BOOTFILENAME](https://ksp-kos.github.io/KOS/structures/vessels/kosprocessor.html).
- In code, `bootFile` is a persistent `[KSPField]`, also exposed as the public `BootFilename` property. Source: [SRC kOSProcessor.cs#L89-L90](https://github.com/KSP-KOS/KOS/blob/8f281a459b6ea0ba917c91bbbc117e68bb948199/src/kOS/Module/kOSProcessor.cs#L89-L90), [#L1181](https://github.com/KSP-KOS/KOS/blob/8f281a459b6ea0ba917c91bbbc117e68bb948199/src/kOS/Module/kOSProcessor.cs#L1181). At boot, `CPU.Boot()` literally compiles and runs the string `run "<path>".`. Source: [SRC src/kOS.Safe/Execution/CPU.cs#L173-L211](https://github.com/KSP-KOS/KOS/blob/8f281a459b6ea0ba917c91bbbc117e68bb948199/src/kOS.Safe/Execution/CPU.cs#L173-L211). Boot runs on the first `FixedUpdate` after the processor (re)enters READY. Source: [kOSProcessor.cs FixedUpdate / ProcessorModeChanged](https://github.com/KSP-KOS/KOS/blob/8f281a459b6ea0ba917c91bbbc117e68bb948199/src/kOS/Module/kOSProcessor.cs#L858-L873).
- **Implications for Claudia:**
  - The boot script re-runs on every scene load and physics load. A Claudia "agent" boot script must therefore be idempotent and able to resume.
  - Boot files are chosen in the editor, so the player (or a ModuleManager patch, or the mod setting `BootFilename` before PRELAUNCH) must assign Claudia's boot script.
  - The docs advise boot scripts to wait a few seconds for physics to settle before touching parts.

Notes:
- The `shared` field on `kOSProcessor` is **private**. The only clean way to get a processor's `SharedObjects` is the addon constructor, which kOS calls for every processor in `InitObjects()`. Source: [kOSProcessor.cs#L562-L600](https://github.com/KSP-KOS/KOS/blob/8f281a459b6ea0ba917c91bbbc117e68bb948199/src/kOS/Module/kOSProcessor.cs#L562-L600). The addon can store `shared` in a static map keyed by `shared.Processor`. Reflection is the alternative.
- Claudia's mod would therefore compile against `kOS.dll` and `kOS.Safe.dll`. That makes kOS a hard dependency, which is expected anyway since the mod is built on kOS. Whether kOS's license permits redistributing those DLLs as reference assemblies is a separate question; kOS is GPLv3. Not researched here.

### 4. Sending terminal input

- **In-process:** use `TermWindow.ProcessOneInputChar(ch, null, allowQueue: true, forceQueue: true)` once per character, then `'\r'` (or `UnicodeCommand.STARTNEXTLINE`) to submit. Source: [TermWindow.cs#L605-L790](https://github.com/KSP-KOS/KOS/blob/8f281a459b6ea0ba917c91bbbc117e68bb948199/src/kOS/Screen/TermWindow.cs#L605-L790).
  - Input is queued in `shared.Screen.CharInputQueue` while the interpreter is busy, so typed commands wait for any running program.
  - `Interpreter.NewLine()` compiles the line only when `ScriptHandler.IsCommandComplete`. Source: [Interpreter.cs#L27-L46](https://github.com/KSP-KOS/KOS/blob/8f281a459b6ea0ba917c91bbbc117e68bb948199/src/kOS/Screen/Interpreter.cs#L27-L46).
  - A BREAK char (Ctrl+C) bypasses the queue and aborts the running program, which gives Claudia a way to abort.
  - The interpreter input is locked while the CPU is OFF or STARVED. Source: [kOSProcessor.cs ProcessorModeChanged](https://github.com/KSP-KOS/KOS/blob/8f281a459b6ea0ba917c91bbbc117e68bb948199/src/kOS/Module/kOSProcessor.cs#L1134-L1165).
- **Out-of-process: the telnet server.** It can be turned on in kOS settings (`CONFIG:TELNET`, port `CONFIG:TPORT` default 5410, loopback 127.0.0.1 by default). It has no authentication at all, by design. Sources: [telnet docs](https://ksp-kos.github.io/KOS/general/telnet.html), [config docs](https://ksp-kos.github.io/KOS/structures/misc/config.html). This is useful if part of Claudia ever runs outside KSP (an external process driving kOS), but it means parsing XTERM escape output. An in-game mod should prefer the in-process call.

### 5. Getting results and errors back

- **What kOS signals by itself:**
  - When a program ends normally, `BreakExecution(false)` pops its context and prints `Program ended.`. When it is aborted manually, kOS prints `Program aborted.`. Source: [CPU.cs#L528-L576](https://github.com/KSP-KOS/KOS/blob/8f281a459b6ea0ba917c91bbbc117e68bb948199/src/kOS.Safe/Execution/CPU.cs#L528-L576).
  - Every context pop calls each registered `IPopContextNotifyee.OnPopContext(context)`, held by weak reference. Source: [CPU.cs#L240-L325](https://github.com/KSP-KOS/KOS/blob/8f281a459b6ea0ba917c91bbbc117e68bb948199/src/kOS.Safe/Execution/CPU.cs#L240-L325). The callback gets the context but **no success or failure flag**.
- **Runtime errors:**
  - Any exception during `KOSFixedUpdate` is caught. `shared.Logger.Log(e)` prints the message (plus a verbose description if `CONFIG:VERBOSE`) to the terminal screen and logs a trace line to `KSP.log` with the prefix `kOS:`. If a program was running, `PopFirstContext()` then **aborts all programs** and returns to the interpreter. Sources: [CPU.cs#L1391-L1421](https://github.com/KSP-KOS/KOS/blob/8f281a459b6ea0ba917c91bbbc117e68bb948199/src/kOS.Safe/Execution/CPU.cs#L1391-L1421), [Logger.cs](https://github.com/KSP-KOS/KOS/blob/8f281a459b6ea0ba917c91bbbc117e68bb948199/src/kOS/Logger.cs), [KSPLogger.cs#L54-L62](https://github.com/KSP-KOS/KOS/blob/8f281a459b6ea0ba917c91bbbc117e68bb948199/src/kOS/KSPLogger.cs#L54-L62).
  - Compile errors in `runpath` surface through the same path.
  - So a crash looks to the mod like "the context popped, the interpreter is waiting for a command again, and the wrapper never reported success."
- **Channels from the script to the mod, best first:**
  1. **A Claudia kOS addon suffix**, e.g. `ADDONS:CLAUDIA:REPORT(LEXICON("status","ok","apoapsis",SHIP:APOAPSIS))`. The C# side receives a kOS `Structure` in-process, synchronously, with no file I/O and no connection needed. This uses the documented addon framework. Source: [Addon Readme.md](https://github.com/KSP-KOS/KOS/blob/8f281a459b6ea0ba917c91bbbc117e68bb948199/src/kOS/AddOns/Addon%20Readme.md).
  2. **`WRITEJSON` to the Archive**, e.g. `0:/claudia/results/<id>.json`. The mod reads it with a file watcher or polling. This needs a home connection; the same out-of-range caveat applies. Source: [serialization docs](https://ksp-kos.github.io/KOS/commands/serialization.html).
  3. **`LOG ... TO "0:/claudia/<id>.log"`** for a progress or telemetry stream. Same caveat. Source: [files docs](https://ksp-kos.github.io/KOS/commands/files.html).
  4. **Scraping the terminal** through `GetScreen()`, or listening on Unity's `Application.logMessageReceived` for `kOS:` lines. Use these only to capture *error text*, never as the primary success signal.
- **Suggested wrapper contract.** Claudia generates `seq_<id>.ks` that sets `CLAUDIA_STATUS` checkpoints. Its last line is the success report, e.g. `ADDONS:CLAUDIA:REPORT(...)`. On the C# side, the "finished" event is the `OnPopContext` notification, or polling `Interpreter.IsWaitingForCommand()`. If that event arrives without a report, the run failed, and the mod attaches the last N terminal lines as the error detail for the Debrief.

## Uncertainties and things not verified

- **No try/catch in kerboscript.** I did not find any exception-handling construct in the language docs I read, and the CPU code aborts all programs on error. This matches my prior knowledge of kOS, but I did not exhaustively check the grammar (`src/kOS.Safe/Compilation/KS/kRISC.tpg`).
- **`IScreenBuffer` text.** `IScreenBuffer` exposes `List<IScreenBufferLine> GetBuffer()` and `DebugDump()` ([IScreenBuffer.cs](https://github.com/KSP-KOS/KOS/blob/8f281a459b6ea0ba917c91bbbc117e68bb948199/src/kOS.Safe/Screen/IScreenBuffer.cs)); I did not verify how cleanly these yield plain text, nor whether `KSP.log` contains the human-readable error message (base `Logger.Log(e)` puts the message on screen; `KSPLogger` adds only the trace text to the Unity log). A prototype should check both.
- **Addon instance lifecycle.** "One addon instance per processor, created in `InitObjects`" comes from reading `AddonManager`'s constructor. I did not test what happens on vessel split, dock, or reload.
- **Off-thread work.** Thread safety was not examined. Claude API calls will be async, so all kOS calls (keystrokes, `Send`, `RunProgram`) must be marshalled back to Unity's main thread.
- **Timewarp and unloaded vessels.** kOS runs only on loaded vessels in physics. Source: [communication docs, Limitations](https://ksp-kos.github.io/KOS/commands/communication.html#limitations). A Maneuver Sequence that spans on-rails timewarp or vessel switching will pause. This is not researched further here.
- All line-number links are pinned to commit `8f281a4`. Source paths are on `develop`, which equals the 1.6.0.1 release timeframe. Older kOS versions (1.4.x/1.5.x) commonly used with KSP 1.12.5 were not diffed.
