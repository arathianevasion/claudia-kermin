# API facts: per-message effort, tools with structured output, and what breaks the cache

Research for #245 (part of map #243). Sources are the Claude API docs on platform.claude.com, read 2026-10-26. Every claim cites the page it comes from. "Not documented" means the docs I read don't settle it.

Scope: `claude-sonnet-5-5` and `claude-opus-5-5`, `thinking: {type: "adaptive"}`, `output_config.format` json_schema, automatic caching plus explicit system breakpoints with the 1-hour TTL, and server-side compaction (`compact_20260112`). These are the settings `MessagesRequest.ToJson()` sends. The beta headers are `server-side-fallback-2026-07-01,compact-2026-01-12,mid-conversation-output-config-2026-07-01` (`ClaudeClient.BetaHeaders`).

How the mod changes effort and schema today:

- Mission requests never set top-level `output_config.effort`. `MissionControl.Send` adds `Message.SystemEffort(turn.Effort)` just before the new user text when the turn's effort differs from the Mission's. That writes `{"role":"system","content":[],"output_config":{"effort":...}}`.
- `MissionControl.Schema` picks `PlanningSchemaJson` or `FlightSchemaJson` for each request. A Question turn reuses the schema the Mission is already in, so the cache holds.
- Tools are always `strict: true` with `tool_choice: auto`.

## 1. Per-message effort: does it keep the cache, and is it valid with adaptive thinking?

**Yes to both, on both models. The one catch: inside a tool loop, the change waits for the next user turn with new input.**

- Per-message effort is in beta on the Claude API for Claude Opus 5.5 and Claude Sonnet 5.5 (among others). It needs the `mid-conversation-output-config-2026-07-01` header, which the mod sends. Without the header the API returns 400 `messages.N.output_config: Extra inputs are not permitted`. — https://platform.claude.com/docs/en/build-with-claude/effort#change-effort-mid-conversation-beta
- It keeps the cache: "Everything before that message is unchanged, so the cached prefix still matches." The prompt-caching invalidation table says the same: "an effort change carried in a `role: "system"` message inside `messages` leaves the cached prefix intact." — effort page (above); https://platform.claude.com/docs/en/build-with-claude/prompt-caching#what-invalidates-the-cache
- It is valid with adaptive thinking. The restriction runs the other way: on Sonnet 5.5 with `thinking: {type: "between_tools"}`, a per-message effort that differs from the level in effect returns 400. "To vary effort for each turn, use adaptive thinking." Opus 5.5 is always adaptive. — effort page, "Recommended effort levels for Claude Sonnet 5.5" and "for Claude Opus 5.5"
- Shape and placement: an empty `content` array plus `output_config.effort`. An effort-only message "renders nothing at its position" and can sit anywhere in `messages`, including first. The usual placement rules for mid-conversation system messages don't apply to it. But "Consecutive `system` messages are judged together", so an effort-only message next to a text-carrying one makes the whole group follow the content rule. — https://platform.claude.com/docs/en/build-with-claude/mid-conversation-system-messages#limitations
- When it takes effect: placed directly after a user turn with new input, it sets the level for the reply to that turn. Placed anywhere else, it takes effect from the next user turn with new input. **"A `user` turn that holds only `tool_result` blocks doesn't count as new input, so a change placed after one in a tool-use loop waits for the next `user` turn with new input."** — effort page; also https://platform.claude.com/docs/en/build-with-claude/preserved-thinking (section "Change effort with a per-message output_config")
- The mod puts the effort message before the new user text. That falls under "anywhere else", so it takes effect from that user turn, which is the intended result.
- Thinking: once sent, the effort message is part of the prefix. Leave it in place, and append a new one to change effort again. Editing or removing a mid-conversation system message after it was sent invalidates the cache from that point. On Opus 5.5 and Sonnet 5.5 it also invalidates the thinking blocks in every later assistant turn. — preserved-thinking page (same section); https://platform.claude.com/docs/en/build-with-claude/mid-conversation-system-messages#combining-with-prompt-caching
- Defaults: Opus 5.5 defaults to `medium` and Sonnet 5.5 to `high`. Setting effort explicitly to the default is the same as omitting it. — https://platform.claude.com/docs/en/build-with-claude/effort#how-effort-works

## 2. Client tools together with json_schema output

**Allowed in the same request. The schema constrains only Claude's direct output, so the reply that ends the turn is the schema JSON. `strict` is optional. Strict tool schemas count toward the same complexity limits as the output schema, compiled-grammar size included.**

- Same request: "JSON outputs (`output_config.format`) and strict tool use (`strict: true`) together in the same request" is listed under "Works with". The docs example sends both to `claude-opus-5-5`. — https://platform.claude.com/docs/en/build-with-claude/structured-outputs#using-both-features-together and #feature-compatibility
- Final reply: "Grammars apply only to Claude's direct output, not to tool use calls, tool results, or thinking tags … Grammar state resets between sections, allowing Claude to think freely while still producing structured output in the final response." — structured-outputs, "Feature compatibility" tip
- Narration between tools: on Opus 5.5 and Sonnet 5.5, text written between tool calls comes back as progress-update `thinking` blocks, empty at the default `display`. On Opus 5.5 there is at most one before each tool call. Sonnet 5.5 keeps short remarks as `text`. — https://platform.claude.com/docs/en/models/opus-5-5/migration-guide (section "Text between tool calls is returned in thinking blocks"); https://platform.claude.com/docs/en/models/sonnet-5-5/migration-guide (same section)
- **Not documented:** whether a `stop_reason: "tool_use"` response that holds a short `text` block (Sonnet 5.5) must match the json_schema, and whether the API rejects or tolerates text that isn't schema JSON in the non-final turns of the loop. A parser should read schema JSON only from the response whose `stop_reason` is `end_turn`, and should tolerate prose `text` next to `tool_use` blocks.
- Forcing a tool: `tool_choice` `any` and `tool` return 400 on Opus 5.5 and Sonnet 5.5. The docs say to use `auto` with strict tools, or structured outputs, instead. `none` is supported. — https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools#forcing-tool-use
- `strict` is not required. Without it the schema isn't enforced: "Without strict mode, Claude might return incompatible types (`"2"` instead of `2`) or omit required fields." — https://platform.claude.com/docs/en/agents-and-tools/tool-use/strict-tool-use
- Complexity limits "apply to all requests with `output_config.format` or `strict: true`" and to "the combined total across all strict schemas in a single request". That means at most 20 strict tools, 24 optional parameters, and 16 parameters with union types. The "additional internal limits on the compiled grammar size", the 400 "Schema is too complex for compilation" that #199 hit, also count "number of tools". The first tip in the docs is "Mark only critical tools as strict." Non-strict tools don't count toward the 20-tool limit. — https://platform.claude.com/docs/en/build-with-claude/structured-outputs#schema-complexity-limits
- **Not documented:** the internal grammar-size budget as a number, and how much one strict tool adds to it. The mod's own probe measured 79 compiling and 89 refused on its `SchemaComplexity.Size` proxy (commit ab6e11d), for the output schema alone. A strict tool's schema adds to the same budget.

## 3. What invalidates which cache layer, and the append-only forms

Cache order is `tools` → `system` → `messages`. A change at one level invalidates that level and every later one. — https://platform.claude.com/docs/en/build-with-claude/prompt-caching#what-invalidates-the-cache

| Change between requests | Tools | System | Messages | Source |
| --- | --- | --- | --- | --- |
| `tools` array: add, remove, rename, edit, or reorder | ✘ | ✘ | ✘ | prompt-caching table; cache-diagnostics `tools_changed` (https://platform.claude.com/docs/en/build-with-claude/cache-diagnostics#response-format) |
| `tool_choice` (also `disable_parallel_tool_use`) | ✓ | ✓ | ✘ | prompt-caching table; https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-use-with-prompt-caching#what-invalidates-your-cache |
| `output_config.format` | not documented | not documented | ✘ | structured-outputs: "Changing the `output_config.format` parameter will invalidate any prompt cache for that conversation thread." The format adds an injected system prompt, but no page says which layers are lost. Treat it as a full miss. (https://platform.claude.com/docs/en/build-with-claude/structured-outputs#prompt-modification-and-token-costs) |
| Top-level `output_config.effort` | model-specific | model-specific | ✘ | prompt-caching table; https://platform.claude.com/docs/en/build-with-claude/thinking#thinking-and-prompt-caching ("Treat any thinking or top-level effort change as starting the cache over") |
| Per-message effort (`role: system` + `output_config`) | ✓ | ✓ | ✓ (prefix intact) | prompt-caching table; effort page |
| Thinking config (mode) | model-specific | model-specific | ✘ | prompt-caching table |
| Appending `tool_use` / `tool_result` turns | ✓ | ✓ | ✓ (append) | Appending keeps the prefix. Thinking blocks get cached along with tool results: https://platform.claude.com/docs/en/build-with-claude/prompt-caching#caching-with-thinking-blocks |
| Non-tool user turn after thinking (Opus 5.5 / Sonnet 5.5) | ✓ | ✓ | ✓ | prompt-caching table: Opus 4.5+ and Sonnet 4.6+ keep thinking blocks |
| A thinking block the API drops (unreadable model, failed prefix check) | ✓ | ✓ | ✘ from that block on | prompt-caching table, "Dropped thinking blocks" |
| Images added or removed anywhere | ✓ | ✓ | ✘ | prompt-caching table |

Grammar cache (separate from the prompt cache): compiled grammars are cached for 24 hours from last use. That cache is invalidated by a change to the JSON schema structure or, "when using both structured outputs and tool use, the set of tools in your request". Changing only `name` or `description` doesn't invalidate it. A miss here costs compile latency, not tokens. — https://platform.claude.com/docs/en/build-with-claude/structured-outputs#grammar-compilation-and-caching

Append-only forms:

- **System instructions:** a mid-conversation `role: "system"` message with text. No beta header is needed on Opus 5.5 or Sonnet 5.5. It must directly follow a `user` turn (one that carries only `tool_result` blocks counts), and it must precede an `assistant` turn or end the array. It can't sit between a `tool_use` and its `tool_result`. — https://platform.claude.com/docs/en/build-with-claude/mid-conversation-system-messages#limitations
- **Effort:** per-message `output_config` (question 1).
- **Tools:** `tool_addition` / `tool_removal` blocks inside a `role: "system"` message. They are in beta on the same models. The `inline-tools-2026-09-15` header covers both references and full definitions by value. `mid-conversation-tool-changes-2026-07-01` covers references only. The `tools` array never changes, so the cache holds. A tool declared with `defer_loading: true` stays withheld until a `tool_addition` surfaces it. A redefinition by value under the same name replaces the schema from that point on. "Keep at least one non-deferred tool in `tools`", or the first tool defined by value costs one full cache miss. — https://platform.claude.com/docs/en/build-with-claude/mid-conversation-system-messages#mid-conversation-tool-changes and #define-tools-in-a-message-beta
- **Turn-scoped reminders:** `clear_at: "next_user_message"`. This is in beta and needs `mid-conversation-system-clear-at-2026-08-21`. Once cleared, the message must stay in place byte for byte. — mid-conversation page, #turn-scoped-system-messages
- **`tool_choice` and `output_config.format`:** no append-only form is documented. The only advice given for `tool_choice` is to place cache breakpoints before the point where it varies. — tool-use-with-prompt-caching
- **Not documented, inference only:** whether `defer_loading` plus `tool_addition` changes the grammar cache key. The docs say: "The grammar builds from the full toolset regardless of which tools are deferred, so prompt caching and grammar caching are both preserved when tools load dynamically." — tool-use-with-prompt-caching, "defer_loading and cache preservation". Whether a tool defined by value mid-conversation rebuilds the grammar is not stated.
- **Beta headers:** the cache-diagnostics page lists "the set of active `anthropic-beta` headers" among the "prompt-affecting request parameter[s]". **Not documented:** whether adding a header mid-session (for example `inline-tools-2026-09-15`) misses the cache. Sending every header from the first request avoids the question.

## 4. Preserved-thinking rules for tool loops

**Send each assistant turn back exactly as received: every block in order, thinking blocks included even when empty. Keep `system` and `tools` fixed. Only append to `messages`.**

- Required: "within a tool-use turn, pass thinking blocks back." Recommended: "across turns, pass everything back". The API filters and bills only the blocks it shows. — https://platform.claude.com/docs/en/build-with-claude/thinking#preserving-thinking-blocks
- Within the latest assistant message, the run of consecutive `thinking` blocks "must match what the model generated in the original request: you can't rearrange, edit, or partially drop them", `redacted_thinking` included. Edits get a 400. The one exception: text placed in the empty `thinking` field of an omitted block is ignored. — same section
- On Opus 5.5 and Sonnet 5.5, `display` defaults to `omitted`, so `thinking` is empty and the `signature` carries the reasoning. A serializer that drops empty blocks or unknown block types, drops empty fields, or reorders blocks edits the prefix. "A block sent back with an empty `signature` fails." A stream parser must keep the block even when no thinking text arrives, because the signature comes in a `signature_delta`. — https://platform.claude.com/docs/en/build-with-claude/preserved-thinking#append-assistant-turns-exactly-as-returned
- What the prefix check covers: the top-level `system`, the set of `tools`, and every message before the block. It does not cover `effort`, `max_tokens`, `output_config`, `tool_choice`, `metadata`, `thinking.display` or `cache_control`. With server-side compaction, "the checked prefix starts at the most recent compaction block." — https://platform.claude.com/docs/en/build-with-claude/preserved-thinking#prefix-check
- What invalidates later thinking blocks in a tool loop: clearing or shortening an earlier `tool_result`, changing an earlier `tool_use` input, adding a text block to an earlier user turn, editing `system` or `tools`, removing a thinking block from the middle, or putting back a block removed earlier. Removing thinking blocks from the start, from the end, or all of them is allowed, though the model loses that reasoning. — https://platform.claude.com/docs/en/build-with-claude/preserved-thinking#what-counts-as-an-edit
- Enforcement: for accounts created on or after 2026-08-31, the default is a 400 (`prefix_mismatch_behavior: "error"`). Older accounts are checked only when the field is set. Players bring their own keys, so some are on new accounts. `"drop_block"` (beta `thinking-binding-controls-2026-08-01`) keeps requests succeeding, but "the prompt cache restarts at the edit" and output tokens go up. — preserved-thinking, #what-the-api-does-with-an-invalid-block and #when-the-api-enforces-the-check
- One thinking configuration per assistant turn: "A tool-use loop is one assistant turn … you can't toggle thinking in the middle of a turn." A mid-turn toggle silently disables thinking for that request. — https://platform.claude.com/docs/en/build-with-claude/thinking#thinking-with-tool-use
- Model switches, such as a server-side fallback: Sonnet 5.5 does not read Opus 5.5 thinking blocks. On the Claude API, Opus 5.5 does read Sonnet 5.5 blocks. Unreadable blocks are dropped without an error or a charge. Keep sending them anyway. — https://platform.claude.com/docs/en/build-with-claude/preserved-thinking#switching-models
- Sonnet 5.5 thinking blocks are bound to the account that produced them, and dropped silently in another account. — preserved-thinking, #account-bound-thinking
- Mid-loop notices on Sonnet 5.5: these models "can treat a system message placed right after a tool result as untrusted text and ignore it." Words from the user go in a `text` block after the last `tool_result` in the same `user` message. Harness notices go in a separate system message after it. — https://platform.claude.com/docs/en/build-with-claude/mid-conversation-system-messages#placement-after-tool-results

## 5. Per-request overhead of a tool round trip beyond tokens

**There is no per-call fee for client tools. Each round trip is a full new request: another time-to-first-token, another cache read of the whole prefix, and a cache write for the new tail. A new schema or tool set also costs a one-time grammar compile.**

- Client tools are "priced the same as any other Claude API request". Only server tools add usage charges. — https://platform.claude.com/docs/en/about-claude/pricing#tool-use-pricing
- Fixed token overhead: with any tool present, the API injects a tool-use system prompt of 286 tokens on Opus 5.5 and Sonnet 5.5 (for `auto`/`none`). The tool definitions, `tool_use` blocks and `tool_result` blocks are billed as ordinary tokens. — pricing page, same section; https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview#pricing
- Latency: "Every tool call is at least one extra round trip; for lightweight tasks the overhead can exceed the work." — https://platform.claude.com/docs/en/agents-and-tools/tool-use/how-tool-use-works. The docs give no per-round-trip latency figure (not documented).
- Grammar compile: "The first time you use a specific schema, there is additional latency while the grammar compiles", then cached for 24 hours. The compile timeout is 180 s. — structured-outputs, #grammar-compilation-and-caching and #schema-complexity-limits
- Cache, per round trip: each request reads the cached prefix at the hit price. On Opus 5.5 and Sonnet 5.5 that is 0.05x base input: $0.20/MTok on Opus 5.5 and $0.10/MTok on Sonnet 5.5. It writes the new tail at the 1-hour write price, 2x base input ($8/MTok on Opus 5.5, $4/MTok on Sonnet 5.5). — https://platform.claude.com/docs/en/about-claude/pricing#model-pricing and #prompt-caching. Cached thinking blocks count as input tokens when read. — https://platform.claude.com/docs/en/build-with-claude/thinking#thinking-and-prompt-caching
- Lookback: automatic caching checks at most 20 block positions back from the breakpoint. A run of consecutive `tool_use` blocks, or of `tool_result` blocks, counts as one position. — https://platform.claude.com/docs/en/build-with-claude/prompt-caching#how-automatic-prefix-checking-works
- Parallel requests: "a cache entry only becomes available after the first response starts." — prompt-caching, #cache-limitations
- Rate limits: every round trip counts toward RPM. Cache reads don't count toward ITPM on these models. — https://platform.claude.com/docs/en/api/rate-limits#cache-aware-itpm
- Effort shapes tool behavior. Lower effort means "fewer and terser tool calls". "In a tool-use loop, follow-up requests that only process tool results can still skip thinking at any level." — https://platform.claude.com/docs/en/build-with-claude/effort#effort-with-tool-use and #effort-with-thinking

## What this means for a tool loop and an effort policy

1. **Effort is set per user turn, not per round trip.** A per-message effort change after a `tool_result`-only user turn doesn't take effect until the next user turn with new input. An effort policy can't raise or lower effort partway through a tool loop. Changing top-level effort instead would restart the cache.
2. **Changing `output_config.format` breaks the prompt cache.** The mod switches between the planning and flight schemas at stage changes, which costs one cache miss per switch (already accepted in #199). A tool loop must keep the same schema on every round trip of one turn.
3. **Strict tools share the output schema's grammar budget.** Adding strict tools to a request that already carries the flight or planning schema pushes it toward the #199 "Schema is too complex" limit, and changing the tool set also recompiles the grammar. Keep the tool list fixed per Mission, mark only critical tools strict, and use `defer_loading` with `tool_addition` (beta `inline-tools-2026-09-15`) to vary what is offered.
4. **On Sonnet 5.5, harness notices placed right after a tool result may be ignored.** In a tool loop, the mod's `SystemText` notice must not be the only carrier of anything that must hold. Notices go in a separate system message after the user message. Words from the player go in that user message as a `text` block.
5. **Assistant turns must be echoed byte-exact**, empty thinking blocks included, and no earlier `tool_result` may be edited later (no trimming of old telemetry results). On new-account keys, a violation is a 400.
